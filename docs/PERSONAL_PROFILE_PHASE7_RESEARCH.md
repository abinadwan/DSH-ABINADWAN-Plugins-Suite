GO for a constrained Phase 7B: automatically contribute response preferences to standard Harness Agent Loop conversations via the official SystemPrompt registry, using a single plugin-owned section and the committed native v2 profile. NO-GO for automatic structured personal-information disclosure in 7B. Phase 7C remains blocked until we can prove both the actual destination and the effect of revocation on retained history, retries, compaction, route changes and disable. Do not substitute prompt wording for permission enforcement. Do not call all conversations supported when an alternate/external agent or a complete system prompt bypasses the registry. Resolve limitations in user-facing wording and acceptance gates.

## 3. Approaches compared

A. Named SystemPrompt.section: recommended for regular response preferences. Official lifecycle, current step assembly, no UI coupling or agent tool call. Does not guarantee application under a complete prompt. Persists model-visible text in history. 
B. systemPrompt.context: dynamic refresh is useful for operational reminders but context is durable user-role text, subject to suppression and potentially retained/compacted; not more private. Do not use required:true to defeat host suppression.
C. system-prompt/assemble waterfall: async customization is available, but complete sections are restored afterward. Could support an approved future admission flow with exact scope; unnecessary for 7B.
D. agent/pre-step: supports admission decisions but changes durable messages; input is consumed on rejection. Avoid for preferences. 
E. Skill registration or AGENTS.md: requires invocation or workspace files; wrong for automatic unified profile.
F. llm/stream: useful for observations or a proven fail-closed veto; not permission to mutate session-derived messages. Adapter override, filesystem changes, monkey patching, undocumented APIs or a global hidden prompt are rejected.

## 4. Proposed Phase 7B architecture

Keep Personal Profile entry and default-off behavior. Register exactly one globally scoped, plugin-owned section named abinadwan:personal-profile-preferences using supported Cordis injection of systemPrompt and a lifecycle-owned registry disposer. Keep existing settings form configuration in independent effect so a missing agent service does not break UI. Section should return empty string unless an eligible native interactive agent and captured model selection are present; scope predicate must be verified for actual Desktop top-level agents, direct chat future, and exclusion of auxiliary/subagent calls. Do not infer from workspace presence. If a reliable predicate cannot be demonstrated, restrict supported modes and report the blocker.

Use a pure shared preferences renderer for runtime and effective preview (currently preview is browser-only; package entry/build/exports must be planned and tested). Accept strictly validated committed v2 only; no v1 implicit migration, no draft, no browser storage, no cross-Profile cache. Investigate the native settings read or own fiber effectiveConfig contract with actual loader and volatile writes; avoid re-reading all secret settings or leaking other namespaces. Prefer own committed entry, no network, no filesystem write. If missing/invalid/disabled, emit nothing. Literal custom text must use interpolate:false, preserve supported formatting, enforce 8192-character existing limit, never silently truncate. Use stable section name/order, do not set complete. Resolve appropriately relative to deployment persona and tool policies; proposed placement after base identity/persona and before operational tool rules, with a test for conflicts. No global workspace selector. User changes become effective on next freshly assembled step, not retroactively and not necessarily on retry of same accepted step. Existing sessions use Host prompt reconciliation; no manual history rewrite. Dispose on disable/reload and prove no duplicate registrations after repeated toggles.

Important privacy distinction: free-form custom instructions may themselves include personal information, secrets, or names. There is no reliable classifier to remove arbitrary sensitive information. For 7B, structured information is never read by renderer; display explicit warning that preferences/custom text can be transmitted to selected model and retained in history. Do not silently enable sending existing free-form text. Recommend a separate unchecked opt-in for sending custom instructions at runtime (or approval of an equally explicit policy); default off pending owner decision. If owner expects allowCloud gate to cover all data including custom text, keep free-form text local until a safe policy is approved; do not misrepresent structured-field switches as covering arbitrary text. Do not treat a style preset called humanizer as automatic skill loading; preserve independent Humanizer behavior and ensure personality preview does not promise enforcement of tool/security policy.

## 5. Instruction priority and conflict handling

Host identity, security, product policies, tool constraints and applicable project instructions remain intact. Profile guidance is subordinate, a preference, not authority over user intent or safety. Current explicit conversation request may override ordinary style/language preferences; user custom instructions cannot grant permissions or bypass safety/approval. Complete prompts and alternate runtime owners remain authoritative. Within preferences, define renderer precedence deterministically and document explicit custom instructions vs presets/traits; existing preview must match runtime exactly for the same approved text. Never put raw profile fields in section, logs or diagnostics. Prompt guidance affects model behavior probabilistically; don't promise deterministic compliance.

## 6. Phase 7C — structured personal information and approval

Trust levels: verified-local (only if connection generation and deployment boundary can actually prove local execution with no forwarding), verified-remote, unknown. Current reviewed public interfaces expose route selection and model info, but no authenticated local-only property or end-to-end no-forwarding guarantee. Treat unknown as ineligible, including configurable aliases, loopback gateways, DNS/redirects, route changes and mutable adapter registrations. Do not equate localhost with guaranteed privacy. No supported general classification proven here. Avoid probing endpoints or exposing credentials. 

Required decision table (per field, per request; default deny):
- master personal-information Off -> omit regardless of all other switches.
- Private -> omit; do not ask; never send local or remote.
- Allow -> eligible only with verified destination plus matching scope/purpose; remote additionally requires explicit cloud-sharing On. Unknown -> omit.
- Ask First -> all master/destination gates first, then native approval for exact agent, field names, route/destination and purpose (no personal values in audit reason). Only allowed-once is eligible; rejection, cancellation, unavailable, invalid result, missing answerer, disabled host approvals -> omit. Recheck snapshot/route and grant immediately before actual send; invalidate on changes, retries or session switch. No persistent consent cache. No request approval on diagnostic assembly.
- Empty value -> omit. Never transfer all fields merely because one is allowed.

Critical blocker: every official model-visible channel examined is logged/durable. SystemPromptProjection may append updated system messages on in-history routes. RuntimeContextProjection supersedes reminders but does not erase past events or model outputs/compaction. A prior allowed local disclosure can remain in derived history, then be resent to a new cloud route after revocation, disabling the plugin, or changing models. A one-shot approval cannot guarantee one actual transmission if ordinary future requests replay history. A tool result has the same durable history problem. The last-mile llm/stream hook cannot legally redact frozen loop requests. Its veto is not a full solution: a plugin-scoped guard vanishes on disable, and exact-value scans cannot detect paraphrases, derived outputs or compaction. A profile-only no-leak guarantee therefore cannot be claimed on rc.3 with these APIs.

Before any structured disclosure: demonstrate an official non-durable, destination-bound admission contract or a supported host-managed history isolation/revocation lifecycle that works across routes, retries and disabled state; independently verify actual adapter trust classification. Otherwise keep PII local and leave 7C blocked; optionally solicit upstream feature. A separately approved relaxed privacy contract with explicit irreversible session retention would be a product decision, not the original enforcement promise. Never silently weaken the requested rules. Existing chat text voluntarily sent by user is outside this profile permission system, and revocation cannot reverse information already delivered to any provider.

## 7. Lifecycle and scope limits

New and existing ordinary native conversations should receive current preferences after the next new step. Retry in same step reuses accepted system section. Disable removes registration for later assemblies but previously recorded prompts/answers remain; in-flight request isn't retroactively unsent. Need real adapter tests for in-history mode, prompt removal, historical replay and compaction; no claims of transcript deletion. Complete prompt providers may suppress this contribution. Alternate runtime owners, external Claude/Codex/ACP subagents, title generation and future Direct Chat are not validated. Future Direct Chat must use normal supported Agent Loop or explicitly integrate under the same privacy gates. No change to provider settings or host files.
