## Direct Chat deployment candidates

The text MVP needs durable ownership, safe creation and first input, session-local model changes, authenticated history and resume, and no terminal or unrestricted filesystem execution. These conditions must hold when the feature plugin is disabled or unavailable, including on cold restart. Tool declaration filtering alone covers only one execution path. The Phase C Workspace-free and internal Workspace alternatives used the ordinary Host. Both inherit its stock resume and native actions when the optional policy is absent. [Phase C ownership evidence](NEW_PLUGINS_PHASE_C_CONTINUATION.md#direct-chat-ownership-admission)

A separate restricted Host is a different security boundary. The new test mounts an ordinary and a model-only composition concurrently on Windows using native packages extracted from `0.2.2-rc.3` build `6b729fe`. Both use the same synthetic working directory and distinct native JSONL roots. The chat composition includes the Agent Loop and its executor with no tool registrations, preset service, filesystem service or subprocess service. An offline adapter receives zero tools at creation, after a model switch, and after restart. A native assistant stream emits the text delta and commits its assistant message. The ordinary composition sees only its own session and native persistence rejects a resume of the chat ID. The chat composition retains both prior messages and the second model in a fresh context. The test uses two in-process service compositions and proves the native primitives. Process isolation, browser routing and endpoint authorization remain open. [Fixture](../../qa/new-plugins-host-check.mjs)

Rolling this out would introduce a second runtime, separate native history, connection authentication, and Host lifecycle and recovery. Harness documents multiple Context-owned client carriers and supplies an embedded native conversation factory. The stock Desktop launcher owns one backend controller, so a second connection needs its own supported client composition. The stock Session Controller also requires filesystem and upload services, and its path-opening Remote resolves a Host path directly. A product prototype must demonstrate a confined or unavailable filesystem service, no terminal or command admission, only intended native Remotes, and no fallback to the ordinary Host or its storage. Disabling a UI control and toggling the model tool roster provide no assurance at those entry points. [Client carriers](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/client/connection/README.md#L28-L34) · [Conversation factory](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/client/ui-conversation/README.md#L105-L113) · [Desktop backend](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/apps/desktop/src/main.ts#L534-L544) · [Session Controller dependencies](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/api/session-controller/src/index.ts#L135-L151) · [Native path actions](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/api/session-controller/src/index.ts#L367-L429)

### Companion Host verification

The owner approved an on-demand companion integrated within the existing Desktop window. Implementation is gated on end-to-end Windows security and isolation proof. Two independent Windows fixtures now establish the following component behavior. [Companion Host checks](../../qa/direct-chat-companion-check.mjs)

- A real child process reused the bundled Node executable and version-matched native Harness packages. An inherited IPC channel was required before startup. The child streamed through a parent-owned synthetic provider via native `llm.prepareCall`, with the synthetic credential absent from the child environment. Two successful child processes shut down with code zero, and the second restored the selected model and both prior replies from separate native JSONL. There was no listener. The fixture has no automatic idle policy or measured Desktop resource budget.
- A separate native Session Controller and Gateway admitted a scoped Peer. It denied creation before policy registration, creation with a different working directory, prompts to a different session, file content, native path opening, and access after revocation and Peer disposal. The generated Client Remotes and shipped Client Session bundle opened a retained chat in a separate Context, selected a model, sent text, and consumed the native assistant text delta. The test supplied an in-process carrier. It did not connect the Desktop renderer to the spawned child.
- Bundled Node `24.21.0` with its permission model and native addons disabled refused to load the Win32 `koffi` dependency in both versions. Native JSONL uses it for its Win32 writer lease. The existing Harness Windows ACL sandbox documents write confinement with unconfined reads. These results leave OS-level process confinement unproven. [Native Windows lease](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/session/session-persistence-jsonl/src/win32.ts#L52-L61) · [Windows sandbox boundaries](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/sandbox/sandbox-windows-acl/README.md#L123-L128)

The existing `SessionProvider` rejects a reference owned by a different Client Session Controller. The native model picker also resolves its Session store and Remote calls from its own Client context. The stock upload client takes its carrier from a page-global hook or the document base URL, so a second Connection alone cannot isolate every native action. A dedicated renderer scope must bind its own Controller, model picker, permissions and text-only capabilities to the companion carrier. The renderer, Desktop authentication and child-process checks must then run together, including scope disposal, reconnect, revocation and no fallback. Provider configuration and credential reuse still need verification with an actual isolated Desktop Host. [Session binding check](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/client/ui-session/src/client/index.ts#L347-L360) · [Model selection scope](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/client/ui-model-selection/src/client/service.ts#L61-L86) · [Upload carrier](https://github.com/deepseek-ai/deepseek-harness/blob/38a6a5c965aa99ab525161efb7cc5cf1fe62fced/packages/client/file-upload/src/client/runtime.ts#L164-L210)

In the companion, the entire native JSONL backend can use one approved canonical root. A new empty location can be considered at first configuration. Moving an existing root requires safe migration, restart and rollback contracts. Preview-only retention can be designed around the companion catalog. Exclusive companion startup would narrow the ownership problem for permanent deletion, including Delete All Direct Chats, while native artifact coverage, reparse containment and metadata reconciliation would still require proof. The prototype does not expose these actions. Two other native surfaces were considered. Continuable subagents have a durable origin and dedicated admission, but prompts require a live parent tree and cold continuation restores the saved preset independently of the original provider. That makes them a delegated workflow with different ownership and resume semantics. LiveShare requires a Workspace and its documented viewer tiers still admit a code runner using the Host's standing file policy. Neither surface provides a tool-free, independent text MVP on stock Desktop. ## Lifecycle deletion decision

The distinct candidate is a backend-owned transactional retirement operation in the optional SQLite persistence provider. SQLite could coordinate updates within its own database. The public provider still implements `create`, `open`, `flush`, `stat` and `list`, and it can retain JSONL source artifacts and share persisted prefixes across forks. Deleting a row in one database cannot establish removal of retained artifacts, preserve other sessions' shared history, or atomically update metadata owned by other services. Switching persistence providers also changes the whole deployment and cannot furnish a supported deletion contract for existing Workspace sessions. Archive and session-list filtering preserve transcripts and therefore cannot satisfy permanent deletion. [SQLite storage, import and fork behavior](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/session/session-persistence-sqlite/README.md#L34-L75) · [Public persistence contract](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/session/session-persistence/src/index.ts#L160-L234)

The missing contracts are a retirement reservation honored by every create, resume, read, scheduled job and restart path, and an authoritative manifest for the admitted Workspace sessions' transcript generations, artifacts and references. Retirement must recheck current ownership, protection and activity, reject Direct Chat and unknown ownership, and provide an idempotent commit or a native recovery protocol across archive, pin, relationships, search and projections. Only session-owned data may be removed, with project paths and Workspace directories outside the operation and reparse points contained by the native storage owner. No safe implementation path was identified. The offline deletion experiments from Phase C were not repeated. [Offline evidence and stop decision](NEW_PLUGINS_PHASE_C_CONTINUATION.md#offline-deletion-feasibility)
